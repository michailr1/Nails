# ADR-010: Уведомления клиентке и связывание с карточкой мастера

- Статус: принято
- Дата: 2026-07-29
- Связано: ADR-004 (клиентский контур без LLM), ADR-009 (привязка клиентки к мастеру), product-principles §10

## Контекст

Клиентский контур дошёл до реального запуска. Ревью PR #245 показало блокер: у бэкенда **нет способа отправить клиентке сообщение** — единственный `sendMessage` живёт внутри runtime бота и отвечает только на входящий update. Значит «мастер подтвердил» не долетает.

Одновременно нужно решить, как связать Telegram-клиентку с уже существующей карточкой у мастера, не нагружая ни клиентку, ни мастера. Текущий механизм (мастер выбирает «Новая / Уже была» при первой заявке) корректен, но это ручное действие на каждую клиентку.

## Решение

### 1. Доставка: outbox, а не прямая отправка из бэкенда

Уведомления клиентке доставляются **push-ом**, клиентка ничего не проверяет вручную.

- бэкенд при событии пишет строку в **таблицу-очередь уведомлений** (outbox): адресат-binding, тип события, безопасные параметры;
- **runtime клиентского бота** опрашивает очередь и отправляет сообщение;
- доставка идемпотентна: повтор не шлёт дубль; неудачная отправка ретраится ограниченно и не блокирует очередь.

**Почему очередь, а не отправка прямо из обработчика approve.** Основание инженерное, не только security:

- вызов внешнего API внутри запроса мастера делает подтверждение заявки зависимым от доступности Telegram: при таймауте либо approve падает **после** уже созданной записи, либо уведомление теряется молча;
- ретраи, идемпотентность и порядок доставки нужны в любом случае — их естественное место — очередь, а не обработчик HTTP;
- у Telegram есть лимиты на частоту отправки; при рассылке throttling обязателен, и он реализуется только на очереди.

**О размещении токена.** Токен клиентского бота остаётся в env клиентского runtime, а не в бэкенде. Это **следствие** выбранной схемы (отправляет тот, кто держит очередь), а не отдельная церемония. Обоснование сознательно ограничено:

- проект уже держит это правило для мастерского бота (токен только в profile `.env`, бэкенд его не получает) — единообразие дешевле исключения;
- бэкенд — компонент с наибольшей сетевой поверхностью, логами, трейсами, CI-секретами и частыми пересборками; long-poll-цикл бота не обслуживает HTTP вообще. Класс утечек через логи/ошибки/дампы env касается бэкенда сильнее;
- токен — переносимая долгоживущая возможность: утёкший однажды, он позволяет писать всем клиенткам от имени мастера из любого места, пока его не отозвать в BotFather.

**Возражение владельца зафиксировано и принято как справедливое**: при компрометации бэкенда на одном VPS атакующий, вероятно, дотянется и до env соседнего процесса, поэтому реальная разница в риске **невелика** и это не жёсткая граница безопасности. Решение сохраняется по инженерным причинам выше; отдельной защитной машинерии вокруг токена не строится.

Экран «Мои заявки и записи» в боте остаётся полезным, но **не заменяет** push и не является условием доставки.

### 2. Классы сообщений разделены

- **Транзакционные** — ответ на действие самой клиентки, она их ждёт: заявка подтверждена, не получилось подтвердить, отменена. Отправляются автоматически, отписка не требуется.
- **Проактивные** — инициируются мастером: обновлённый прайс, «давно не были» и подобное. Отправляются **только по явному решению мастера** (см. §4).

### 3. Связывание с карточкой — по убыванию надёжности

Признак связывания выбирается по тому, насколько он доказывает принадлежность карточки, а не по удобству.

**3.0. Ограничение масштаба — работа мастера не растёт с числом клиенток.**
Любой механизм, требующий отдельного действия мастера **на каждую клиентку**, отвергается: при 50–200 карточках это неподъёмно, а мастер с 10 клиентками в продукте не нуждается. Персональная ссылка-приглашение на каждую карточку рассмотрена и **отклонена** именно поэтому.
Работает **одна общая ссылка мастера** (ADR-009), которую она распространяет привычными каналами (профиль, сторис, рассылка в мессенджере) — один раз на всех, а не по ссылке на клиентку.
Связывание при этом **не создаёт мастеру новых действий**: оно встроено в решение первой заявки, которое мастер выполняет в любом случае.

**Персональная ссылка остаётся возможностью по желанию.** В разделе «Клиентки» у карточки доступна кнопка «пригласить» — она выдаёт ссылку, привязанную к этой карточке, и снимает вопрос привязки сразу. Это **не путь онбординга по умолчанию** и не обязанность: мастер пользуется ею, когда ей так удобнее (одна конкретная клиентка, сложный случай, клиентка просит). Обязательного действия на каждую карточку не возникает, поэтому ограничение §3.0 не нарушается.
Ограничения персональной ссылки: **одноразовая** (первый перешедший забирает), с ограниченным сроком жизни, отзываемая; мастер видит, кто по ней привязался, и может отменить привязку. Причина одноразовости — пересланная ссылка иначе отдаёт карточку и историю визитов не тому человеку.

**3.1. Подтверждённый Telegram-контакт (основной автоматический путь).**
Клиентка одним тапом делится номером; Telegram сам подтверждает принадлежность номера аккаунту (`contact.user_id == from.id`). При совпадении с телефоном ровно одной активной карточки — **связываем автоматически** и **уведомляем мастера** с возможностью отменить (не спрашиваем разрешения заранее). Совпадение с несколькими карточками — не связываем.

**3.2. Номер, введённый вручную — подсказка, не основание.**
Telegram может быть зарегистрирован на другой номер, поэтому клиентка может **ввести номер, который знает мастер**. Такой номер **не подтверждён** и сам по себе связывания не даёт: иначе достаточно набрать чужой номер, чтобы получить чужую карточку и историю визитов.
Введённый номер используется как **сильная подсказка**: мастеру в решении первой заявки нужная карточка **предвыбирается** с указанием причины («клиентка указала номер, совпадающий с этой карточкой»), и подтверждение занимает один тап. Это не добавляет мастеру шагов — механизм «Новая / Уже была» уже существует, ему лишь подставляется ответ.

**3.3. Имя — никогда.** Совпадение имени не связывает и не предвыбирает карточку.

**3.4. Нет признака** — работает существующий путь: мастер выбирает «Новая клиентка / Уже была у меня» при решении первой заявки.

Во всех случаях сохраняются инварианты: приватные заметки мастера клиентке не отдаются; карточка, уже связанная с другой активной identity, не может быть выбрана; связывание owner-scoped.

Это уточняет ADR-004 §3.2 (где телефон был только подсказкой): подтверждённый Telegram-контакт повышен до основания для автосвязывания, введённый вручную номер остаётся подсказкой.

### 4. Проактивная рассылка — только по решению мастера

Продуктовый принцип §10 («Нэйли не пишет клиентке сама») сохраняется в сути: **инициатива и содержание принадлежат мастеру**, Нэйли — исполнитель.

- рассылка **всегда инициируется мастером** («покажи новый прайс клиенткам», «напомни тем, кто давно не был»);
- Нэйли готовит материал и **показывает мастеру ровно то, что уйдёт**, вместе со списком получательниц и их числом;
- отправка — **одно явное подтверждение** мастера; без него ничего не уходит;
- у клиентки есть **отказ от проактивных сообщений**, который не влияет на транзакционные;
- частота ограничена, чтобы рассылка не превращалась в спам от имени мастера;
- автоматических рассылок по расписанию без участия мастера не существует.

### 5. Ограничение Telegram: доставка возможна только тем, кто открыл бота

Telegram не позволяет боту написать пользователю, который сам не начал с ним диалог. Следствия, обязательные к учёту:

- любое уведомление (и транзакционное, и проактивное) доходит **только до клиенток, уже перешедших по ссылке мастера**;
- «догнать» через бота клиентку, которая бота не открывала, невозможно — для неё у мастера остаются её обычные каналы;
- поэтому охват проактивной рассылки всегда меньше числа карточек, и интерфейс мастера обязан показывать это честно: сколько получательниц реально достижимо, а не общее число клиенток.

### 6. Интерфейс мастера: достижимость и отправка

**Отметка «в боте» в разделе «Клиентки».** Мастер видит, до кого сообщение вообще может дойти. Это **состояние, а не переключатель** — не чекбокс, которым мастер «подключает» клиентку. Отметка обязана **самокорректироваться**: Telegram сообщает о блокировке бота только в момент отправки, поэтому результат доставки из outbox гасит признак в «недоступна». Иначе мастер считает охват по фантомам. Доступен фильтр «только подключённые».

Для неподключённых мастеру предлагается **один общий текст приглашения** с её ссылкой (скопировать и разослать своими каналами) — один раз на всех, а не действие на каждую карточку. Персональная ссылка (§3.0) остаётся дополнительной возможностью по желанию.

**Отправка живёт там, где живёт содержимое, а не в отдельном разделе рассылок.** Отдельный маркетинговый модуль отклонён: он противоречит §1/§12 продуктовых принципов (Нэйли помогает работать, а не администрируется), провоцирует массовые сообщения — а заблокировавшая бота клиентка становится недостижимой навсегда — и дублирует уже существующий список «Давно не были». Кнопка отправки размещается рядом с предметом:

- «Мой прайс» → «Показать клиенткам»;
- «Давно не были» → «Напомнить»;
- карточка клиентки → «Написать» (персональное сообщение).

**Отдельного журнала отправленного нет.** Первоначально он был здесь предложен, но обоснование смешивало два класса сообщений и не выдержало проверки. Транзакционные отправки мастеру аудировать незачем: она сама нажала «Подтвердить», результат виден в состоянии заявки и записи, а доставка — системная телеметрия (для неё есть health/observability runtime, а не экран в кабинете). Вопрос «отправляла ли уже?» возникает только у проактивной рассылки, и ответ на него обязан появляться **в момент решения об отправке** («этим пятерым вы писали 3 дня назад»), а не в отдельной истории — по тому же правилу, что и вся отправка: информация живёт там, где принимается решение.
Недоставка мастеру видна там, где она действенна — отметкой на карточке клиентки («сообщения не доходят»), а не списком событий.

**Просьбы о записи не выносятся отдельным пунктом меню.** Заявка — это просьба о записи на конкретное время, то есть событие календаря, а не задача по управлению клиентками. Поэтому основное место — **«Календарь»**: спокойная строка «2 просят записаться — посмотреть» (тот же паттерн, что §10 статистики: одна мысль плюс действие) и пометка на самом дне, визуально не занимающая время. Дополнительно просьба видна в карточке клиентки. Отдельная вкладка не создаётся.
Название на языке мастера — «**просят записаться**», не «Заявки».

**Ссылку собирает бэкенд, а не интерфейс.** Кабинету отдаётся готовый `https://t.me/<client_bot>?start=<token>`; username бота берётся из конфигурации окружения. Отдавать в интерфейс голый токен нельзя — им нельзя воспользоваться; хардкодить username в JS нельзя — при смене бота ссылки молча разъедутся.

**Язык достижимости — про возможность написать, а не про «подключение».** «Подключена» — системное слово, мастеру оно ничего не говорит. Используются: «**кому можно написать**» (фильтр), «**на связи в Telegram**», «**сообщения не доходят**», «**нет в Telegram**». Внутреннее состояние «ещё не проверено» мастеру не показывается — это наша неуверенность, а не её забота.

**Текст приглашения — про способ связи, а не про Нэйли.** Клиентка не знает, что такое Нэйли, и знать не должна: для неё это бот мастера. Приглашение говорит о записи в Telegram и содержит готовую ссылку.

**Сегменты — только осмысленные для продукта**: «все подключённые» и «давно не были». Конструктор произвольных выборок (CRM-аналитика) не строится.

## Границы (не входит)

- публичный каталог мастеров и поиск;
- перенос/отмена подтверждённой записи клиенткой (отдельное решение: запрос мастеру, а не прямое изменение `Booking`);
- LLM в клиентском контуре (ADR-004 неизменен);
- массовый rollout клиентского бота.

## Инварианты

Telegram-токен клиентского бота — только в клиентском runtime; owner-scoping на каждом запросе; приватные поля карточки клиентке не раскрываются; связывание существующей карточки — только по достоверному признаку или явному решению мастера; заявка не становится записью без подтверждения мастера.
