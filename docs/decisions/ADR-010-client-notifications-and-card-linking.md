# ADR-010: Уведомления клиентке и связывание с карточкой мастера

- Статус: принято
- Дата: 2026-07-29
- Связано: ADR-004 (клиентский контур без LLM), ADR-009 (привязка клиентки к мастеру), product-principles §10

## Контекст

Клиентский контур дошёл до реального запуска. Ревью PR #245 показало блокер: у бэкенда **нет способа отправить клиентке сообщение** — единственный `sendMessage` живёт внутри runtime бота и отвечает только на входящий update. Значит «мастер подтвердил» не долетает.

Одновременно нужно решить, как связать Telegram-клиентку с уже существующей карточкой у мастера, не нагружая ни клиентку, ни мастера. Текущий механизм (мастер выбирает «Новая / Уже была» при первой заявке) корректен, но это ручное действие на каждую клиентку.

## Решение

### 1. Доставка: outbox, а не прямая отправка из бэкенда

Уведомления клиентке доставляются **push-ом**, клиентка ничего не проверяет вручную.

- бэкенд при событии пишет строку в **таблицу-очередь уведомлений** (outbox): адресат-binding, тип события, безопасные параметры;
- **runtime клиентского бота** опрашивает очередь и отправляет сообщение;
- **инвариант: Telegram-токен клиентского бота не попадает в бэкенд** — он живёт только в env клиентского runtime (тот же принцип, что у мастерского контура: токен только в profile `.env`; прецедент — `feedback_tool`);
- доставка идемпотентна: повтор не шлёт дубль; неудачная отправка ретраится ограниченно и не блокирует очередь.

Экран «Мои заявки и записи» в боте остаётся полезным, но **не заменяет** push и не является условием доставки.

### 2. Классы сообщений разделены

- **Транзакционные** — ответ на действие самой клиентки, она их ждёт: заявка подтверждена, не получилось подтвердить, отменена. Отправляются автоматически, отписка не требуется.
- **Проактивные** — инициируются мастером: обновлённый прайс, «давно не были» и подобное. Отправляются **только по явному решению мастера** (см. §4).

### 3. Связывание с карточкой — по убыванию надёжности

Признак связывания выбирается по тому, насколько он доказывает принадлежность карточки, а не по удобству.

**3.0. Ограничение масштаба — работа мастера не растёт с числом клиенток.**
Любой механизм, требующий отдельного действия мастера **на каждую клиентку**, отвергается: при 50–200 карточках это неподъёмно, а мастер с 10 клиентками в продукте не нуждается. Персональная ссылка-приглашение на каждую карточку рассмотрена и **отклонена** именно поэтому.
Работает **одна общая ссылка мастера** (ADR-009), которую она распространяет привычными каналами (профиль, сторис, рассылка в мессенджере) — один раз на всех, а не по ссылке на клиентку.
Связывание при этом **не создаёт мастеру новых действий**: оно встроено в решение первой заявки, которое мастер выполняет в любом случае.

**3.1. Подтверждённый Telegram-контакт (основной автоматический путь).**
Клиентка одним тапом делится номером; Telegram сам подтверждает принадлежность номера аккаунту (`contact.user_id == from.id`). При совпадении с телефоном ровно одной активной карточки — **связываем автоматически** и **уведомляем мастера** с возможностью отменить (не спрашиваем разрешения заранее). Совпадение с несколькими карточками — не связываем.

**3.2. Номер, введённый вручную — подсказка, не основание.**
Telegram может быть зарегистрирован на другой номер, поэтому клиентка может **ввести номер, который знает мастер**. Такой номер **не подтверждён** и сам по себе связывания не даёт: иначе достаточно набрать чужой номер, чтобы получить чужую карточку и историю визитов.
Введённый номер используется как **сильная подсказка**: мастеру в решении первой заявки нужная карточка **предвыбирается** с указанием причины («клиентка указала номер, совпадающий с этой карточкой»), и подтверждение занимает один тап. Это не добавляет мастеру шагов — механизм «Новая / Уже была» уже существует, ему лишь подставляется ответ.

**3.3. Имя — никогда.** Совпадение имени не связывает и не предвыбирает карточку.

**3.4. Нет признака** — работает существующий путь: мастер выбирает «Новая клиентка / Уже была у меня» при решении первой заявки.

Во всех случаях сохраняются инварианты: приватные заметки мастера клиентке не отдаются; карточка, уже связанная с другой активной identity, не может быть выбрана; связывание owner-scoped.

Это уточняет ADR-004 §3.2 (где телефон был только подсказкой): подтверждённый Telegram-контакт повышен до основания для автосвязывания, введённый вручную номер остаётся подсказкой.

### 4. Проактивная рассылка — только по решению мастера

Продуктовый принцип §10 («Нэйли не пишет клиентке сама») сохраняется в сути: **инициатива и содержание принадлежат мастеру**, Нэйли — исполнитель.

- рассылка **всегда инициируется мастером** («покажи новый прайс клиенткам», «напомни тем, кто давно не был»);
- Нэйли готовит материал и **показывает мастеру ровно то, что уйдёт**, вместе со списком получательниц и их числом;
- отправка — **одно явное подтверждение** мастера; без него ничего не уходит;
- у клиентки есть **отказ от проактивных сообщений**, который не влияет на транзакционные;
- частота ограничена, чтобы рассылка не превращалась в спам от имени мастера;
- автоматических рассылок по расписанию без участия мастера не существует.

### 5. Ограничение Telegram: доставка возможна только тем, кто открыл бота

Telegram не позволяет боту написать пользователю, который сам не начал с ним диалог. Следствия, обязательные к учёту:

- любое уведомление (и транзакционное, и проактивное) доходит **только до клиенток, уже перешедших по ссылке мастера**;
- «догнать» через бота клиентку, которая бота не открывала, невозможно — для неё у мастера остаются её обычные каналы;
- поэтому охват проактивной рассылки всегда меньше числа карточек, и интерфейс мастера обязан показывать это честно: сколько получательниц реально достижимо, а не общее число клиенток.

## Границы (не входит)

- публичный каталог мастеров и поиск;
- перенос/отмена подтверждённой записи клиенткой (отдельное решение: запрос мастеру, а не прямое изменение `Booking`);
- LLM в клиентском контуре (ADR-004 неизменен);
- массовый rollout клиентского бота.

## Инварианты

Telegram-токен клиентского бота — только в клиентском runtime; owner-scoping на каждом запросе; приватные поля карточки клиентке не раскрываются; связывание существующей карточки — только по достоверному признаку или явному решению мастера; заявка не становится записью без подтверждения мастера.
