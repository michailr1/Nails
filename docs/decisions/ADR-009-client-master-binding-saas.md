# ADR-009: Привязка клиентки к мастеру и публичная витрина мастера (SaaS)

- Статус: принято
- Дата: 2026-07-24
- Связано: ADR-004 (клиентский контур без LLM), engineering-principles §1 (константа масштаба — см. «Пересмотр §1»)

## Контекст

Продуктовое направление уточнено: **самообслуживаемый SaaS** — автоматическая подписка и автоматическое подключение мастеров без участия владельца, цель — 100+ мастеров. Это меняет исходную рамку ADR-004 §3.1 («один мастер, owner из server-config, без tenant routing»).

Факты Telegram, которые определяют архитектуру привязки:

- один аккаунт BotFather держит ~**20 ботов** (до **40** с Premium);
- **создание бота нельзя автоматизировать** — BotFather интерактивный, метода Bot API «создать бота» нет; перенос ботов throttled (≤5/день).

Следствие: **бот на каждого мастера несовместим с авто-онбордингом и не масштабируется** на 100+. Нужна привязка через один платформенный бот, публичная витрина мастера (у мастера сейчас только `telegram_user_id`, клиентского имени нет) и осмысленное состояние «нет привязки».

## Решение

### 1. Один платформенный бот + deep-link

- **Один бот на платформу** (один токен). Ботов на мастера нет.
- Мастер при подключении получает уникальный **непрозрачный start-токен** → ссылку `t.me/<PlatformBot>?start=<token>`.
- Клиентка открывает ссылку → bot runtime передаёт `start`-payload → backend резолвит `owner_user_id` из токена **только на сервере** и привязывает identity к мастеру.
- Масштаб неограничен: новый мастер = строка `start_token → owner_user_id`, не новый бот. Онбординг полностью автоматизируем.
- Изоляция — на backend (owner-scoped, ADR-004). Бот — транспорт; owner **никогда** не берётся из ввода клиентки (инвариант ADR-004 §3.1, распространён на multi-master).

### 2. Multi-binding: клиентка может ходить к нескольким мастерам

- `client_telegram_identities` уникальна по паре `(owner_user_id, telegram_user_id)` — один Telegram-пользователь держит **несколько** отношений, по одному на мастера. Жёсткой привязки «один клиент → один мастер» нет и не вводится.
- **Активный контекст:** deep-link задаёт/переключает мастера; холодный вход при одной привязке — сразу она (нулевое трение); при нескольких — короткое меню «**ваши мастера**» **только из собственных привязок клиентки** (не глобальный реестр). Разумно — sticky last-used.
- **Изоляция между мастерами:** мастер A не видит, что клиентка ходит к B; список «ваши мастера» виден только клиентке. Multi-binding ничего не протекает между owner-scope.
- Запирание отвергнуто: неестественно (реальная клиентка ходит к нескольким/меняет мастера), вредно для SaaS (убивает кросс-мастерский сетевой эффект) и дороже (потребовало бы глобального unique по `telegram_user_id` против текущей модели).

### 3. Публичная витрина мастера

У мастера в `users` только `telegram_user_id` + `role` — клиентского имени нет. Вводится отдельная сущность публичной проекции:

- **`master_public_profile.display_name`** — как мастера видят клиентки («Ногти у Насти»). **Обязателен**; растёт позже (аватар, короткое описание, район).
- **Гейт активации:** ссылка мастера **не активна**, пока `display_name` не задан. Нет имени → нет рабочей ссылки → показать raw-ID негде.
- **Один источник** клиентской проекции: то же имя — шапка публичного прайса, приветствие бота, подтверждения заявки, уведомления, QR/карточка шеринга. Второе «имя мастера» не заводится.
- Глобальная уникальность имени **не требуется** (записываются по ссылке, каталога нет).
- Собирается just-in-time при включении клиентского контура (голосом Нэйли, мастер-контур), редактируется в любой момент, с подтверждением «так вас увидят клиентки».

### 4. Инвариант идентичности мастера

> Клиентке **никогда** не раскрывается числовой `telegram_user_id` мастера и его личное имя/username, полученные автоматически из аккаунта. Клиентке показывается **только** то, что мастер сам положил в публичную витрину.

- числовой `telegram_user_id` — внутренний идентификатор доверенного резолвинга, не раскрывается никогда;
- `@username` — **публичный контакт по выбору мастера**: показывается ссылкой `t.me/<username>` только если мастер сам добавил его в витрину (`public_contact`, опционально). Не выводится автоматически — у многих @ личный или отсутствует.

### 5. Состояние «нет привязки» — воронка к ссылке, не витрина мастеров

Маркетплейс-picker отвергнут (перечисление/приватность), поэтому «нет привязки» ведёт за ссылкой мастера, а не показывает каталог. Три под-случая и тексты — в приложении.

### 6. Контакт с мастером

- **Дефолт — структурированный форвард** (ADR-004 §5): клиентка пишет в боте → пересылается мастеру; личный Telegram скрыт, заявки структурированы, записи не утекают из системы (stickiness SaaS).
- **Прямая `@`-ссылка — opt-in мастера** через `public_contact`, с честным предупреждением мастеру: прямой контакт = записи мимо системы.

## Модель данных (expand-only, owner-scoped)

- `master_link_tokens (token PK, owner_user_id FK, created_at, revoked_at)` — маппинг start-токена в owner; резолвится только сервером.
- `master_public_profile (owner_user_id PK/FK → users.id, display_name NOT NULL, public_contact NULL, …)`.
- `client_telegram_identities` — multi-binding уже выражен unique по паре `(owner_user_id, telegram_user_id)`; изменений схемы не требует.

## Границы (сейчас не строим)

- биллинг, автоподписка, тарифы, админ-дашборд SaaS — тяжёлая tenant-машина **не начинается**; строятся только дешёвые примитивы привязки;
- публичный каталог/обнаружение мастеров — отдельный поздний продукт со своей модерацией/безопасностью;
- per-master white-label бот — опция для желающих (мастер вручную создаёт бота в BotFather, отдаёт токен платформе, рантайм мультиплексирует токены → owner), не путь по умолчанию.

## Рассмотрено и отклонено

- **Бот на каждого мастера** — лимит 20/40 на аккаунт, нет API-создания, throttled-перенос; несовместимо с авто-онбордингом и 100+.
- **Маркетплейс-picker мастеров в боте** — перечисление и приватность; ADR-004 уже отверг.
- **Авто-вывод @username/личного имени мастера** — без явного согласия мастера; не у всех есть/хотят.
- **Запирание «один клиент → один мастер»** — неестественно, вредно для SaaS, дороже.

## Пересмотр §1

Этот ADR предполагает SaaS-направление, что противоречит константе engineering-principles §1 («один мастер, multi-tenant не для этого этапа»). Здесь строятся **только дешёвые примитивы привязки** (один бот + start-токен + витрина), тяжёлая tenant-машина не начинается, поэтому пилот остаётся соразмерным. Но саму §1 как нормативную константу нужно пересмотреть **отдельным решением** — иначе часть правил «не строй на будущее» вступит в противоречие с продуктом. До этого пересмотра новые SaaS-подсистемы (биллинг, реестр, дашборд) не начинаются.

## Приложение — тексты клиентской стороны

Тон — платформенный нейтрально-вежливый (не «Нэйли»; ADR-004 §6).

**Нет привязки, ссылки/токена нет:**
> 👋 Здравствуйте! Это бот для записи к мастеру. Запись открывается по личной ссылке вашего мастера — обычно она в его профиле, сторис или визитке. Откройте эту ссылку — и я покажу запись именно к вашему мастеру. Если ссылки нет — попросите у мастера «ссылку для записи».

**Ссылка недействительна/просрочена:**
> Эта ссылка больше не действует. Попросите у мастера актуальную ссылку для записи 🙏

**Доступ закрыт мастером (revoked):**
> Запись к этому мастеру сейчас недоступна. Если это ошибка — свяжитесь с мастером напрямую.

**Валидная ссылка, мастер известен (приветствие с витриной):**
> 👋 Здравствуйте! Вы записываетесь к **{display_name}**.
> [💅 Прайс] [📅 Записаться] [🗂 Мои записи]
