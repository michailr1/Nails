# Бизнес-процессы

Дата актуализации: **20 сентября 2026 года**.

## 1. Статус документа

Основные процессы мастера и клиентский Telegram-контур реализованы. Документ описывает текущие бизнес-инварианты, а не ранний MVP-план.

## 2. Общие правила

- identity/role не берутся из текста сообщения;
- данные всегда owner-scoped;
- модель или Telegram bot не объявляют операцию успешной без ответа доменного API;
- dangerous master mutations требуют явного подтверждения;
- idempotency защищает от повторных нажатий/повторов доставки;
- внутренние поля клиентки не попадают в публичный контур;
- pending client request не является Booking;
- никакого auto-link существующей клиентки по имени/телефону.

## 3. Onboarding мастера

Мастер может сохранить имя/стиль общения, обычные часы, услуги/цены и стартовые записи.

Черновик и подтверждённое состояние разделены. Повторный onboarding не используется как способ обычного редактирования — для этого есть постоянные настройки и доменные операции.

## 4. Управление расписанием

Мастер может:

- посмотреть день/неделю/месяц;
- задать обычные рабочие часы;
- добавить исключение по конкретной дате;
- поставить целый выходной;
- изменить несколько интервалов в день;
- запросить свободные окна;
- создать запись на явно заданное время, если нет day-off/overlap.

Существующие записи не двигаются автоматически при изменении положительных availability intervals.

## 5. Клиентские карточки мастера

Карточка содержит публичную часть и private working notes.

Поиск/создание защищены от случайного дубля. Client Telegram identity не присоединяется к существующей карточке автоматически — решение принимает мастер.

## 6. Создание/перенос/отмена Booking мастером

Перед записью/переносом сервер:

1. resolve owner/client/service;
2. рассчитывает полную длительность и buffers;
3. проверяет day-off;
4. проверяет overlap;
5. формирует summary;
6. после подтверждения выполняет transactional mutation;
7. делает fresh readback.

Отмена мягкая; историческая запись не уничтожается.

## 7. Клиентский вход по ссылке

```text
master invite link
 -> Telegram /start <token>
 -> server resolves token
 -> binding/context for exact owner
 -> public master profile
```

Нельзя выбирать owner через client request arguments.

Без binding клиентка получает путь к ссылке мастера, а не каталог мастеров.

## 8. Выбор услуги клиенткой

Клиентский bot:

1. показывает public base services;
2. создаёт server-side draft;
3. показывает совместимые addons/quantities;
4. backend пересчитывает composition/price/duration;
5. клиентка выбирает дату;
6. backend возвращает free slots для полной длительности;
7. клиентка выбирает slot;
8. bot показывает итог и предупреждает, что мастер ещё должен подтвердить;
9. submit создаёт pending BookingRequest.

Bot сам не рассчитывает цену/длительность и не резервирует slot.

## 9. Обработка заявки мастером

В кабинете мастер видит входящую заявку и может:

- связать Telegram identity с существующей карточкой;
- создать новую карточку;
- проверить/скорректировать состав и время в разрешённых границах интерфейса;
- approve;
- reject.

При approve сервер снова проверяет availability. Если slot уже занят, Booking не создаётся и автоматический перенос запрещён.

## 10. Уведомления клиентке

После изменения статуса outbox доставляет транзакционное сообщение через client runtime.

Клиентка получает результат approve/reject без необходимости заново открывать bot.

## 11. «Мои записи»

Клиентский интерфейс показывает только owner-scoped записи/заявки этой Telegram identity. Другой Telegram user и другой owner не должны видеть или менять их.

## 12. Связь с мастером

Прямой публичный контакт показывается только через `public_contact`, который мастер заполняет сам.

Structured forward/короткая поясняющая заметка клиентки является информацией для мастера и не меняет состав, цену, длительность или slot.

## 13. Invite links

Мастер может использовать:

- общую ссылку для новых клиенток;
- персональную one-time link для конкретной карточки.

Без заполненного public profile интерфейс должен вести мастера к обязательной настройке, а не оставлять немую disabled-кнопку.

## 14. Приватность

Клиентка не получает:

- internal aliases/notes;
- чужие bookings/requests;
- database IDs как пользовательскую информацию;
- numeric Telegram ID мастера;
- автоматический Telegram username мастера.

## 15. Что ещё не входит в текущий рабочий контур

- billing/subscriptions;
- public master directory;
- per-master bots;
- LLM-команды клиентки;
- автоматическое подтверждение заявок;
- pending slot hold;
- массовые маркетинговые рассылки.
